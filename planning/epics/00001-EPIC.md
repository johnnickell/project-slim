# Align Engineering and Delivery

## Destination

Adopt one consistent engineering and delivery model for the Slim starter: explicit package ownership, thin HTTP
boundaries, behavior-focused tests, a single locked dependency environment, a coherent running-container quality
gate, record-owned planning, and independent review before publication.

The human maintainer approved this destination and explicitly rejected retaining lowest/latest dependency lanes
and no-dev certification. This record authorizes a planning handoff, not implementation, dependency updates,
publication, or runtime/tooling changes. The maintainer subsequently approved the six-area decomposition and then
explicitly replaced bootstrap-first sequencing with immediate authoring of requirement TICKETs and proposed TASKs
under a transitional convention. The maintainer then explicitly rejected dual-schema support: migrate old planning
to EPIC/TICKET/TASK with provenance, and support only that schema. Implementation remains separately authorized;
epic or requirement readiness alone is not permission to execute work.

Completion means the approved rules are Slim-owned, documented, implemented where applicable to existing behavior,
and verified locally and in hosted CI. Future product features remain outside this epic.

## Decisions so far

### Architecture and package ownership

- Preserve `App\` mapped to `src/` and inward `Adapter -> Application -> Domain` dependencies.
- Use public Fight package messages, handlers, capabilities, and safe Views directly. Do not copy package source or
  introduce consumer aliases whose only purpose is forwarding or renaming.
- Introduce owned Application orchestration only for demonstrated Slim policy or coordination across real ownership
  boundaries, with observable inputs, outcomes, failures, and injected inward capabilities.
- Keep service location in composition and justified adapter machinery, never Domain or Application behavior.
- State transaction, retry, durability, and delivery guarantees explicitly; CQRS alone establishes none of them.
- Record the accepted ownership rules in a Slim-local ADR. Do not create empty layers or speculative abstractions.

### HTTP, PHP, and naming

- Use thin single-interaction Actions and dedicated Responders for real application interactions. Preserve the
  existing simple root response rather than manufacturing a use case or presentation layer for it.
- Keep business policy, transaction control, and persistence out of HTTP Actions and Responders. Enforce protected
  use-case authorization beyond HTTP middleware, including non-HTTP entry paths.
- Cross presentation boundaries with safe Views and explicit mapping; keep PHP properties camelCase and HTTP JSON
  and database fields snake_case. Scope JSend to an explicitly documented transport contract.
- Sanitize unexpected public errors, distinguish malformed input from server failures, and document intentional
  compatibility changes to existing error responses with regression evidence.
- Prefer strict types, final classes, readonly properties and value objects, constructor injection, and
  capability-named owned interfaces without an `Interface` suffix, with justified Doctrine entity exceptions.
- Adopt multiline docblocks with capitalized active-verb summaries without terminal periods, constructor summaries
  naming the class, and multiline `@inheritDoc` for inherited behavior. Do not rename upstream contracts.

### Product tests and the canonical gate

- Product suites prove owned behavior and important package integration contracts at proportionate unit,
  integration, and functional boundaries. For bugs, add a failing regression test before repair when possible.
- Validate architecture, dependency rules, container/configuration wiring, generated artifacts, wrappers, planning,
  quality tooling, and test infrastructure directly through their owning tools rather than product-suite tests.
  Moving the same tooling tests into a separately named PHPUnit suite is not alignment.
- Retain meaningful existing behavior and integration evidence. Remove tests whose sole purpose is the retired
  certification profile, and do not manufacture behavior or test fixtures to satisfy a coverage percentage.
- Report meaningful owned unit coverage separately from integration/functional coverage, including denominator,
  driver availability, exclusions, and justified gaps. Aim for complete meaningful unit coverage where practical;
  an enforced numeric threshold requires an explicit follow-up decision. PR #11's subsequently merged lean-gate
  handoff, now [TASK-00016](../tasks/00016-TASK.md), requires exact direct-Unit coverage; reconcile that needs-info
  conflict and its overlapping scope before gate/coverage implementation rather than silently override either plan.
- Use a thin `./bin/build` wrapper and a PHP phase orchestrator in the already-running Compose service. Run named,
  fail-fast planning, PHP syntax, qualified Fight PHPCS style, static-analysis, architecture, Rector dry-run, and
  behavior-test phases. Configure checks against real owned boundaries, not placeholder source.
- Use one coherent PHPUnit/coverage execution for all configured product suites. Coverage policy reads that run's
  report rather than rerunning tests. Focused wrappers remain iteration tools.
- Keep local and hosted verification on the same canonical `./bin/build` command. CI may explicitly prepare its
  environment and start services before invoking that command. Prove clean-checkout setup and worktree isolation.
- Dependency installation, updates, and audits are explicit maintenance operations, not build phases.

### Retire framework-support certification

- Support one committed application dependency lock and its installed development environment. Retire lowest/latest
  dependency lanes, the lowest lock and digest, no-dev certification, and framework-support receipt checking or
  generation machinery retained solely for that certification profile.
- Do not replace the retired matrix with an equivalent matrix or require substitute no-dev certification. This is
  an intentional narrowing of the ongoing dependency-support claim, not merely a faster implementation of it.
- Preserve the historical outcomes of [TASK-00012](../tasks/00012-TASK.md) (former T-00002) and
  [TASK-00014](../tasks/00014-TASK.md) (former T-00005). Their ongoing matrix/receipt obligations in
  [TICKET-00014](../tickets/00014-TICKET.md) (former PRD-00002) are superseded by this approved decision; update operative
  guidance and tooling together in separately authorized implementation work. Historical success must not be
  presented as fresh verification of the replacement gate.
- Qualify a stable released dependency baseline as separate authorized work. Inspect exact installed public
  signatures and prove compatibility before updating dependencies; neither development aliases nor another
  consumer's versions establish release compatibility. No Fight Common 2.0 migration is authorized here.

### Planning and delivery

- Support only `EPIC -> TICKET -> TASK`: destinations, requirements, then bounded implementation outcomes. Migrate
  existing PRD/T-ticket records into the correct roles; do not retain a dual parser, legacy execution frontier,
  archive mode, or compatibility alias. An old executable ticket does not become a requirement by simple relabeling.
- Preserve historical meaning, statuses, acceptance evidence, and dependency relationships through an explicit
  old-to-new provenance mapping and repaired references. Old IDs are provenance, not supported live identities;
  old live paths need not remain. Preserve strategy prose outside generated projections.
- [The conventions](../CONVENTIONS.md) support only the new schema. [The mapping](../MIGRATION.md) records the completed
  data conversion, not parser aliases. [The current Board](../tickets/BOARD.md) exposes TASKs as executable work.
  Generated views, archive tooling, and review guidance remain separate implementation work; disclose current gaps.
- Adopt independent Spec and Standards review against requirements, exact implementation snapshots, tests, and
  evidence. The implementation author cannot independently accept their own work.
- Keep implementation completion, independent review, commit, publication, merge, archive, release, and deployment
  as distinct states and authorities, with traceable review and delivery handoffs.
- Choose the authorized checkout/worktree before implementation; use bounded feature branches from `develop`,
  preserve unrelated work, and keep scratch ignored. Archive only on explicit request.

### Application-specific boundaries and existing planning

- Retain MySQL as the planned persistence choice; alignment does not impose PostgreSQL or a second database lane.
- Reconcile the existing [AccessControl application map](../wayfinder/slim-access-control-application-map.md) with the
  approved rules without pretending its open decisions are closed. WF-002 owns detailed runtime choices; WF-003
  owns the HTTP/ADR contract; WF-001 and WF-004 own released contracts and persistence compatibility; WF-010 owns
  the eventual application implementation handoff.
- Existing local-safe transaction wiring does not establish compatibility with future package handlers. Qualify
  exact `UnitOfWork` versus `TransactionalUnitOfWork` signatures before wiring those use cases; do not conceal a
  type mismatch with a container alias.
- Exclude implementation of authentication, production persistence, workers, realtime, the SPA, browser journeys,
  release/publication, deployment, runtime enrollment, and package-source changes from this alignment epic.

## Approved requirement decomposition

The human maintainer approved these six requirement areas and authoring them immediately under the transitional
convention. These are requirements, not six implementation tasks or assumed one-PR outcomes. Their linked TICKETs
own detailed acceptance; the separate ten-TASK decomposition has now been approved and recorded in the
[TASK index](../tasks/README.md).

### 1. [Consistent Planning and Independent Review — TICKET-00007](../tickets/00007-TICKET.md)

- Problem/outcome: distinguish requirements, implementation, review, and publication without losing existing work.
- Include migration to the sole supported hierarchy, old-to-new provenance/reference repair, record-owned priority,
  generated views, independent Spec/Standards review, and traceable handoffs. Exclude legacy compatibility modes,
  automatic archiving, publication, and merge.
- Evidence: migrated meaning and history are traceable through the provenance map, generated frontiers agree with
  new-only validation, and review and implementation completion remain separate.
- Sequence: requirements and TASKs may be authored before tooling exists. New-only schema migration/validation,
  generated views, archive tooling, and review guidance are implementation slices, not an authoring gate. The superseded
  PRD-00003/T-00006 bootstrap sequence remains addressable history, not executable work.

### 2. [Explicit Application Ownership and PHP Standards — TICKET-00008](../tickets/00008-TICKET.md)

- Problem/outcome: contributors can place behavior correctly and follow enforceable local conventions.
- Include the ownership ADR, direct package composition, justified orchestration, injection, HTTP responsibilities,
  PHP naming/documentation, and reconciliation with open Wayfinder decisions. Exclude speculative layers,
  package-source changes, and new product use cases.
- Evidence: existing source conforms; automated enforcement is distinguished from semantic review.
- Sequence: establish the standards used by the quality-gate and HTTP work; do not preempt open product decisions.

### 3. [Single-Lock Development Without Framework Certification — TICKET-00009](../tickets/00009-TICKET.md)

- Problem/outcome: verify the application rather than maintain a framework-support matrix.
- Retire lowest/latest lanes, the lowest lock/digest, no-dev certification, and certification-only receipts, scripts,
  and tests. Preserve historical outcomes and meaningful behavior evidence. Exclude substitute certification lanes
  and dependency-version changes.
- Evidence: one authoritative lock, no operative matrix/receipt obligations, and working setup/application checks.
- Sequence: remove candidate-specific certification constraints before qualifying a released dependency baseline.

### 4. [Qualified Released Dependency Baseline — TICKET-00010](../tickets/00010-TICKET.md)

- Problem/outcome: consume deliberately selected, compatible package releases instead of treating aliases as releases.
- Include release availability, public signatures, compatibility assessment, explicit maintenance commands, and a
  selected committed lock. Exclude blindly matching another consumer, Common 2.0, package publication, and future
  persistence implementation.
- Evidence: released artifacts install, existing behavior passes, and future handler incompatibilities remain
  explicit rather than hidden behind aliases. Unavailable releases block this area rather than justify a dev alias.
- Sequence: depends on area 3; final gate and HTTP verification use the selected released lock.

### 5. [Reproducible Runtime and One Quality Gate — TICKET-00011](../tickets/00011-TICKET.md)

- Problem/outcome: developers and hosted CI verify the same application through one predictable command.
- Include running-Compose execution, worktree isolation, PHP orchestration, syntax/style/static-analysis/architecture/
  Rector checks, behavior-focused suites, and separate unit-coverage reporting. Run PHPUnit once and keep dependency
  maintenance outside the gate.
- Exclude future full application topology, frontend tooling, deployment, arbitrary coverage thresholds, and tests
  of quality tools. Evidence includes clean-checkout CI, concurrent isolation, clear failures, complete suite
  execution, and honest coverage reporting.
- Sequence: depends on areas 2 and 3; final acceptance uses area 4's selected lock. Runtime details must reconcile
  with WF-002 without implementing its excluded future services.

### 6. [Safe and Predictable HTTP Failures — TICKET-00012](../tickets/00012-TICKET.md)

- Problem/outcome: distinguish client errors from server failures without exposing internal exception text.
- Include malformed-input handling, safe representations, documented JSend scope, regression evidence, and preserved
  root/routing behavior. Exclude new API operations, authentication, business-authorization implementation, and
  test-only production routes.
- Evidence: observable status/body contracts, secret-safe failures, and unchanged intended routing behavior.
- Sequence: follows area 2's HTTP rules, reconciles with WF-003, and uses area 5's canonical gate for final
  verification against the selected lock.

No area introduces new business commands, queries, events, permissions, or state-changing product journeys.
Security applies to error disclosure, secrets, dependency trust, review authority, and execution isolation;
business-authorization implementation remains deferred. Validation concerns planning integrity, package
compatibility, quality evidence, and the existing HTTP boundary as applicable.
