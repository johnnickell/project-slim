# Make Development Runtime Worktree-Safe

## Outcome and Scope

Make the existing starter runtime and repository lifecycle/exec/test wrappers predictable on clean and concurrent
checkouts. Covers [TICKET-00011](../tickets/00011-TICKET.md) AC-01 and the runtime prerequisite for AC-02; the complete
quality-gate replacement remains TASK-00009.

In scope: the current Compose development service, project/port/resource isolation, explicit setup, documented
lifecycle/test/exec behavior, missing-service failures, safe local defaults, and environment guidance needed for
this boundary. Dependency installation remains an explicit setup operation.

Out of scope: the future Nginx/FPM/database/queue/realtime topology, production deployment, authentication, new
product features, the full gate orchestrator, implicit volume deletion, and new product tests of wrappers.
No business commands, queries, events, or permissions apply; security concerns local binding, secrets, and isolation.

## Acceptance Criteria

- [ ] **AC-01:** A clean checkout can install dependencies explicitly, start the existing service, reach the preserved
  root response, run focused tests, execute commands, and stop its own runtime through documented repository wrappers.
- [ ] **AC-02:** Two authorized checkouts run concurrently without fixed host-port, Compose project, container, or
  persistent-resource collisions. Identity/override rules are deterministic and documented; shared unrelated
  resources are never inferred to belong to this TASK.
- [ ] **AC-03:** Lifecycle/exec/test wrappers have explicit running-service and missing-prerequisite behavior, preserve
  command exit results, and do not silently install dependencies or provision unrequested future services.
- [ ] **AC-04:** Defaults bind development access locally, required secrets are not committed or logged, and cleanup
  only affects ownership-proven disposable runtime resources. Durable data/volumes require separate deletion authority.
- [ ] **AC-05:** Runtime guidance and the bounded decisions relevant to WF-002 agree, while its larger open topology
  remains open. The current canonical build continues to work until TASK-00009 replaces its execution model.
