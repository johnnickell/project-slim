# Sanitize HTTP Failures

## Outcome and Scope

Stop arbitrary exception-message disclosure at the existing HTTP boundary and classify malformed JSON as client
input failure while preserving intended root and routing semantics. Covers [TICKET-00012](../tickets/00012-TICKET.md)
AC-01 through AC-05.

In scope: Slim-owned error translation and composition, the bounded malformed-JSON/failure contract, regression
coverage at the narrowest actual seam, functional routing evidence, and compatibility documentation. Use exact public
contracts from the selected installation; do not repair this by copying or editing package internals.

Out of scope: new API operations, authentication/authorization implementation, complete AccessControl/OpenAPI design,
production persistence, synthetic root use cases/Responders, test-only production routes, or package releases.
No business command, query, event, permission, or product state transition is introduced.

## Acceptance Criteria

- [ ] **AC-01:** Before repair, reproduce existing message passthrough and malformed-JSON server-error behavior with
  failing regression tests where technically possible; record the old/new expectation and justify any inability
  to reproduce. Sentinel values are synthetic and must not be real secrets.
- [ ] **AC-02:** Malformed JSON produces HTTP 400 with a stable documented safe client-error representation. Unexpected
  downstream failures produce HTTP 500 with a stable generic representation. Neither public body nor headers contain
  arbitrary exception messages, stack traces, credentials, configuration values, or internal identifiers.
- [ ] **AC-03:** Before changing behavior, record the exact chosen safe JSend envelopes/messages and their transport
  scope in the TASK evidence and local HTTP contract. The choices must implement the bounded 400/500 distinction,
  not expand the API or infer status from arbitrary exception text. Document the deliberate wire change from old tests.
- [ ] **AC-04:** The root remains HTTP 200 with its existing body. Unknown-route 404 and unsupported-method 405 outcomes
  use explicit safe mappings and preserve relevant routing headers such as `Allow`; fixture-only API routes remain
  absent from production bootstrap. Other framework failures receive safe documented handling, not raw passthrough.
- [ ] **AC-05:** Tests reach actual owned error translation and relevant pipeline behavior, asserting statuses, safe
  bodies, applicable headers, and absence of synthetic sensitive text. No product endpoint is created solely to
  exercise a failure; Domain policy/lookup decisions are not recreated in the transport mapper.
- [ ] **AC-06:** Focused regressions and the final canonical gate pass on the selected released lock. Reconcile the
  bounded error contract with WF-003 without claiming its complete future HTTP/OpenAPI decisions are closed.
