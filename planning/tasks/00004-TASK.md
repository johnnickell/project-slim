# Establish Ownership and PHP Conventions

## Outcome and Scope

Make the accepted ownership model and PHP conventions explicit in Slim and align existing owned code without
changing behavior. Covers [TICKET-00008](../tickets/00008-TICKET.md) AC-01 through AC-04.

In scope: one Slim-local ownership ADR, focused engineering guidance, references from existing instructions, and
bounded style/documentation changes to owned source. State package-versus-consumer responsibilities, the narrow
orchestration test, injection rules, HTTP responsibility boundaries, and review versus tooling enforcement.

Out of scope: dependency changes, installing quality tools, new product use cases, synthetic layers or abstractions,
renaming public PSR/package contracts, moving unrelated source to fit a diagram, HTTP behavior repair, or production
persistence/authentication. No new business command, query, event, permission, or transaction is introduced.

## Acceptance Criteria

- [ ] **AC-01:** The local ADR records direct package use, inward dependencies, injected capabilities, composition
  exceptions, prohibited forwarding aliases, and when owned orchestration genuinely adds Slim policy/coordination.
- [ ] **AC-02:** Guidance assigns thin Actions, safe Views, explicit mapping, Responders for real interactions, server
  authority across entry paths, and transaction/external-effect responsibility without claiming CQRS guarantees.
- [ ] **AC-03:** PHP guidance and existing owned source use strict types, final/readonly defaults with justified entity
  exceptions, capability names, camelCase properties, snake_case boundary fields, and the approved multiline docblocks.
  No upstream code is restyled or renamed.
- [ ] **AC-04:** Existing observable behavior and public contracts remain unchanged. The root stays a simple response;
  no synthetic command/Responder or speculative Domain/Application tree is introduced.
- [ ] **AC-05:** Enforcement responsibility distinguishes tool-checkable syntax/dependencies from semantic review.
  WF-003 and future persistence/package questions remain explicitly open; the bounded ADR does not close the whole
  API/OpenAPI investigation. HTTP failure repair remains TASK-00010.
